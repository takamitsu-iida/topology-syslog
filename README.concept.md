# トポロジー駆動型シスログサーバー

## 機能要件定義書

---

## 1. エグゼクティブサマリー (Executive Summary)

### 1.1 背景と課題

従来のシスログサーバー（Rsyslog,Logstash等）は、大量のログを単一のテキストメッセージとして受信・保存することに特化しており、ネットワークの接続形態（トポロジー）を認識できない。そのため、1箇所の大規模障害（例:コアスイッチのダウン）が発生した際、配下の多数の機器から複数のアラートが同時送信され、運用者が真の「根本原因（Root Cause）」を特定するまでに多大な時間を要する（アラートストーム問題）。

### 1.2 本システムのビジョン

本システムは、YANGモデル(iida-network-topology)に準拠したトポロジー情報をインメモリグラフ（Python NetworkX等）として保持し、受信したSYSLOGをリアルタイムでトポロジー構造にマッピング・集約する。これにより、**「1000件のアラートログ」を「1件の根本原因インシデント」に自動変換して通知する、自律推論型のインフラ監視プラットフォーム**を実現する。

## 3. 機能要件 (Functional Requirements)

### F-1: トポロジーデータ管理機能 (Topology Management)

* **F-1.1: YANGモデルインポート**

  * RFC 8345 (Network Topologies) および RFC 8346 (L2 Topology)に準拠したJSON/XML形式のトポロジー構成データをインポート可能であること。

* **F-1.2: ライブトポロジー同期**
  * NETCONF/RESTCONF または gNMI (gRPC Network Management Interface)経由で定期/イベント駆動で構成情報を更新し、インメモリグラフをミリ秒単位で再構築すること。

* **F-1.3: マルチレイヤーグラフ構築**

  * 物理層（L1）、データリンク層（L2）、IPネットワーク層（L3）のレイヤー間依存関係（Underlay / Overlay）を保持すること。

### F-2: SYSLOG受容・構文解析機能 (Log Ingestion & Parsing)

* **F-2.1: 高並列ログ受信**

  * UDP/TCP/Syslog-over-TLS (514番ポート等) をサポートし、ピーク時 10,000 EPS (Events Per Second) 以上の処理能力を持つこと。

* **F-2.2: メッセージ構造化 (NLP / Dynamic Parsing)**

  * 受信した生のSYSLOGから「タイムスタンプ」「送信元IP/ホスト名」「ファシリティ/セビリティ」「イベントテンプレート（例: Interface Down / BGP Neighbor State Change）」を自動抽出すること。

### F-3: トポロジー相関・根本原因推論エンジン (Correlation & Root Cause Inference)

* **F-3.1: スライディング・タイムウィンドウ処理**

  * 受信ログを一定時間（設定可能: 例 30秒〜120秒）のタイムウィンドウバッファに保持し、非同期・順不同で届くログ群を一括でグループ化すること。

* **F-3.2: グラフ木構造追跡（NetworkX）**

  * ログ送信元ホスト群をNetworkXグラフ上にプロットし、最上流に位置する親ノード（`nx.ancestors`）を自動特定すること。

* **F-3.3: 根本原因 (Root Cause) の判定ロジック**

  * バッファ内のノード集合 $N$ に対し、以下を判定する。

    1. 他のどのログ発生ノードの下流にもなっておらず、かつ自身が他のログ発生ノードの上流であるものを **「プライマリ・インシデント（根本原因）」** と定義。

    2. プライマリノードのトポロジー配下から発生しているログを **「セカンジ・アラート（二次被害）」** として1つのインシデントオブジェクトに紐付ける。

### F-4: インシデントライフサイクル管理 & 通知 (Incident & Alerting)

* **F-4.1: インシデント起票と集約**

  * 1つの根本原因に対し、1つのユニークな インシデントID（例: `INC-20260814-001`）を発行すること。

* **F-4.2: ノイズキャンセル通知**

  * 通知先（Webhook / Slack / ITSM / メール）へは、セカンダリ・アラート群を省略し、「根本原因機器・発生事象・影響を受ける配下機器数」をサマリした1通の通知のみを送信すること。

### F-5: 可視化UI/ダッシュボード (Incident-Centric UI)

* **F-5.1: インシデントベース表示**

  * 従来の「ログ行のタイムライン」ではなく、「発生中のインシデント」を最優先でカード表示するUIを提供すること。

* **F-5.2: トポロジー・ビジュアル・トレース**

  * インシデント選択時、ネットワーク構成図上で「根本原因ノード（赤点滅）」と「二次影響ノード（黄点滅）」および「切断されたリンク」をハイライト表示すること。

## 4. 非機能要件 (Non-Functional Requirements)

### N-1: 性能・拡張性 (Performance & Scalability)

* **処理遅延**: ログ受信からインシデント推論・通知完了までの遅延時間は、設定されたスライディングウィンドウ時間 + 1秒以内とする。

* **メモリ使用量**: 10,000ノード、50,000リンク規模のトポロジーグラフを保持・演算する際のRAM使用量を 2GB 以下に抑えること。

### N-2: 信頼性・可用性 (Reliability & Availability)

* **ステートレス相関エンジン**: トポロジーデータはYANGソースから再ロード可能とし、分析プロセスの再起動時にも即座に復元できること。

* **バッファオーバーフロー対策**: アラートストーム時（100,000 EPS以上）はメモリ保護のため、リングバッファ構造を採用し古いログからドロップまたはディスクへ退避（Spooling）すること。
